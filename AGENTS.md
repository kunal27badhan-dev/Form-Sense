# AGENTS.md

## Project shape
- Flutter app in `lib/` with a simple screen flow: `lib/main.dart` → `lib/screens/splash_screen.dart` → `lib/screens/login_page.dart` → `lib/screens/register_page.dart` or `lib/screens/home_page.dart`.
- Firebase is initialized at startup with `DefaultFirebaseOptions.currentPlatform`; there is no separate service layer or route table.
- UI is mostly screen-local widgets plus one shared auth background in `lib/widgets/auth_background.dart`.

## Read first
- `pubspec.yaml` for assets/dependencies: `video_player`, `firebase_core`, `firebase_auth`.
- `lib/main.dart` for app bootstrap and the actual home entry point.
- `lib/firebase_options.dart` and `android/app/google-services.json` for Firebase wiring.
- `lib/screens/splash_screen.dart`, `login_page.dart`, `register_page.dart`, `home_page.dart` for navigation and app behavior.

## Current conventions
- Navigation is done directly with `Navigator.push` / `pushReplacement`; there are no named routes or state-management packages.
- `SplashScreen` plays `assets/videos/splash.mp4` with `video_player` and replaces itself with `LoginPage` when playback completes.
- `LoginPage` uses `FirebaseAuth.instance.signInWithEmailAndPassword`; `RegisterPage` is a local placeholder that only checks two hard-coded IDs (`kunal_27`, `7827`) and then returns to login.
- `AuthBackground` layers `assets/images/bg_image.jpeg` under a translucent overlay; keep that stack order when changing auth screens.
- `HomePage` is currently a mostly static dashboard with an empty `BottomNavigationBar.onTap`.

## Integration notes
- `lib/firebase_options.dart` is generated by FlutterFire CLI; do not hand-edit it unless you are intentionally changing generated config.
- Linux is not configured in `DefaultFirebaseOptions.currentPlatform`; Android/iOS/macOS/web/windows are present.
- If Firebase project settings change, regenerate both Flutter options and platform config together so `firebase_options.dart`, `firebase.json`, and Android/iOS files stay aligned.

## Workflow that matters here
- Use `flutter pub get` after dependency or asset changes.
- Use `flutter analyze` to catch issues; the repo follows `package:flutter_lints/flutter.yaml` via `analysis_options.yaml`.
- Use `flutter test` before relying on the test suite: `test/widget_test.dart` is still the default counter-app smoke test and is not aligned with the current UI.
- For Firebase updates, prefer `flutterfire configure` over manual edits to generated config files.
